# RAID — mcp-lineage Workstream

<!-- meta-id: 0b094282dc86ccb3 -->

**Scope:** One interaction — an LLM/agent calls an MCP tool that touches a data resource. Client, server and data resource only. **MCP gateways, proxies and federation are out of scope** (see `README.md` § Scope); entries touching them are recorded and deferred, not actioned. Reference implementation + demo supporting [OpenLineage #4484](https://github.com/OpenLineage/OpenLineage/issues/4484) and [MCP #2638](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/2638).

## How to Use This File

This is a **register**, not a log. Entries are **live records that are updated
in place** as the position changes — a risk's likelihood moves, a mitigation
lands, an issue closes, an assumption gets tested.

**Reading it:** `grep -n` for the ID you need. Do not read end to end unless
you are auditing it.

**Publication:** this is the published copy of the register, curated for a
public audience — trimmed of entries with no bearing on the workstream's
findings, never of corrections or invalidated assumptions. See the lab's
`CURATION.md` for the general policy this curation follows.

### The four registers

This register applies BearingNode's **Anatomy of Uncertainty** framework. Each
quadrant demands a different response, so filing something in the wrong register
means responding to it the wrong way:

| Quadrant | Register | What it demands |
|----------|----------|-----------------|
| Known Knowns | **Decisions** | execution |
| Known Knowns | **Issues** | issue management, corrective action |
| Known Unknowns | **Risks** | mitigation |
| Unknown Knowns | **Assumptions** | surfacing — you cannot mitigate an assumption you do not know you are making |
| Unknown Unknowns | reversibility built into decisions | resilience, not planning |

The framework is set out in a three-part series on the BearingNode blog:

1. **[Anatomy of Uncertainty: Why 95% of GenAI Pilots Fail](https://www.bearingnode.com/post/anatomy-of-uncertainty-why-data-ai-projects-need-a-new-navigation-map)**
   — the four quadrants, and why data and AI projects need a different
   navigation map.
2. **[The Eight Uncertainty Scenarios in Data & AI Projects](https://www.bearingnode.com/post/the-eight-scenarios-mapping-positive-and-negative-uncertainty-in-data-ai-projects)**
   — each quadrant splits into a **positive and a negative** scenario, giving
   eight situations that demand different governance approaches; traditional
   PMO works for four of them and actively harms the other four.
3. **[Your PMO is Killing Your AI: The Governance Mismatch](https://www.bearingnode.com/post/anatomy-of-uncertainty-part-3-why-ai-projects-need-different-governance)**
   — why AI projects need different governance from delivery projects.

**Uncertainty here is two-sided, and the registers carry both.** Per Part 2,
each quadrant splits into a positive and a negative scenario. There is
deliberately **no separate Opportunities register** (I19) — where an entry has
upside as well as downside, say so **in the entry**. R06 is the pattern: the
same fact that makes per-server instrumentation an adoption risk makes gateways
a concentration opportunity, and both belong in one place because they are one
fact. Look for the upside when writing an entry; do not file it separately.

### Rules

- **IDs are stable and never reused.** They are cited from commit messages,
  code comments and GitHub issues. Renumbering breaks them.
- **Update entries in place.** Never silently rewrite.
- **A decision is not complete until its implications are logged.** Where a
  decision *creates* a risk or issue, open it and tag it `Created by Dnn`, and
  list it in that decision's **Implications** column. A decision whose costs
  live only in its Rationale reads as free, and the next reader cannot find
  what it cost.
- **Record wrong assumptions as wrong — never delete them.** The correction is
  the most valuable content here (see A02, A04, A06).
- **Negative decisions are decisions** (D02, D16). Deliberately accepting
  something is a decision too. An accepted risk stays **Open — accepted**
  rather than being closed to tidy the register.
- **Dates are absolute, `YYYY-MM-DD`.**
- Anything needing tracking beyond this file becomes a **repo issue**.

| R04 | A reviewer reads D08 as doing exactly what D02 and A01 rejected: deriving dataset identity by parsing SQL text. | R06 | D01 puts dataset-identity emission in the server, because only the server executes the query. Or does an MCP gateway carry part of it instead? | D01, D02. | Certain. This is a property of the design, not a possibility. What is uncertain is which way it cuts. | Downside: an RFC whose adoption path is "fork every server you run" will not be adopted, however correct it is. The parentage half is built (D10); actor identity is not (D28). The emission half is structural, not eliminated, and adopting it is down to the ecosystem (A12). |
| R07 | The demo's lineage consumer may not understand the mechanism the RFC now rests on. `ParentRunFacet` 1-2-0 (which D10 relies on) landed upstream 2026-07-08. | R08 | A reviewer in a regulated setting rejects fail-open as the wrong default. The design holds that a lineage failure must never break the tool call, so a query can execute with no record that it executed. In a control environment, that is the state a control exists to prevent. | Created by D11. | Medium-high once `REQUIREMENTS.md` reaches its intended audience. This is the first question a control function asks of any observability side-channel. | High on credibility rather than correctness. An unstated fail-open default reads as an oversight. A stated one with the alternative offered reads as engineering judgement. | Made the posture configurable, not assumed. `LINEAGE_FAILURE_MODE` selects fail-open or fail-closed on the driver. An unrecognised value refuses to start rather than silently defaulting. The START-before-execution ordering makes fail-closed real rather than theatrical: the failure to record is caught before the data is reached. There are two carve-outs. The failure path itself stays fail-open in both modes, because a lineage error must never mask the underlying database error. The drop is also counted before the mode is consulted, so fail-closed can never become the reason a loss goes unrecorded. We verified this end to end against `mcp-server-failclosed` in compose: the same image, pointed at a collector that does not exist, with `FailureMode` set to `closed`. The tool call was refused, and the server log showed exactly one emission failure (START) and no execution. 5 unit tests plus 1 integration test cover both postures. | Closed. Both postures are implemented and verified, and neither is presented as the correct default. |
| R09 | Identity may be deliberately absent from telemetry, and the correlation reference that replaces it may dangle. (a) Mature OTel deployments routinely strip identity-bearing attributes as a data-protection control. This is the same instinct R02 states as our own design principle, so a well-governed deployment may have actor identity absent by policy, not oversight. (b) Where identity is stripped, the remaining link is `trace_id`/`span_id`. That link resolves only if the trace was retained, and sampling is the norm. Our own `otel-collector-config.yaml` tail-samples at 10%, so roughly nine in ten lineage events carrying a trace reference would point at a trace Jaeger never stored. | R02, D01, D10. Compounds R01. | High. (a) is standard practice in any regulated deployment and (b) is the default in almost all of them. | High, and it cuts at the fallback rather than the primary path. If `_meta` carries lineage parentage the primary path is unaffected, but the whole argument for trace correlation as a safety net assumes the trace is both identity-bearing and retained, which in a well-run organisational deployment it is frequently neither. | Do not treat trace correlation as an identity mechanism. It is a correlation mechanism, and only where the trace is retained. The design intent is that the lineage event carries a pseudonymous actor reference supplied by the caller in `_meta`, resolvable in a separate access-controlled system, which would survive both stripping and sampling because it never depended on the span. Nothing sends that reference today, so the event is tagged `lineage.actor: absent` (D28). | Open, partially mitigated. Leg (b), durability, is addressed: a `lineage.dropped` span attribute plus a first-position `string_attribute` tail-sampling policy keep any trace recording lineage loss, unconditionally, while everything else stays at 10%. We verified this in Jaeger. Leg (a), deliberate identity stripping, is untouched, and is exactly why identity has to travel in `_meta`, not the span. |
| R10 | The objectives get confused, and the workstream is read as duplicating something that already exists. | R11 | The trace-context proposal is read as an attempt to make OpenLineage a telemetry tool, the opposite of its intent. *Unknown knowns — things believed without being tested. Surfacing them is the

| ID | Assumption | Basis | Status | What we found | Impact if invalidated |

| A01 | A generic external proxy could infer dataset identity accurately enough from MCP tool-call traffic (e.g. by parsing SQL text) to drive OpenLineage emission. | Seemed a reusable ecosystem-wide instrumentation pattern, by analogy with existing generic OTel-MCP proxy packages. | Invalidated. | Rejected (see D02). Inferring what was touched by parsing traffic external to the entity performing the action is the same category of error as deriving OpenLineage events from OTel spans, already ruled out earlier in this workstream's thinking. | Would have built the entire demo on the wrong emission point. |
| A02 | Job-mediated lineage has been identity-agnostic "by design," because scheduled pipeline jobs are impersonal. | Initial framing when reasoning about why OpenLineage never needed actor identity. | Invalidated. | Job ownership has always mattered. OpenLineage already has `OwnershipJobFacet` (from Airflow's owner field, [#1035](https://github.com/OpenLineage/OpenLineage/issues/1035)) and `TagsDatasetFacet`, with active work syncing tag/ownership config across clients ([#4280](https://github.com/OpenLineage/OpenLineage/issues/4280), [#4432](https://github.com/OpenLineage/OpenLineage/pull/4432)). | A03 | Microsoft's Entra Agent ID "autonomous vs. interactive/ on-behalf-of" taxonomy is fully mirrored in OTel's GenAI semantic conventions, so both can be cited as already aligned. | Assumed adoption without checking. | Partially validated. | Confirmed against `model/gen-ai/registry.yaml`: `gen_ai.agent.id`/`.name`/`.description`/`.version` all exist, but no authority-model attribute exists anywhere, and `mcp.common.attributes` carries no caller identity at all. Adopt Microsoft's language (D05). State the OTel alignment as partial: the identity primitive exists, but the authority-model distinction does not. | Overstating the alignment would misrepresent OTel to both communities. |
| A04 | OpenTelemetry has no attribute identifying which data resource an MCP call touched, so we planned to invent one (`data.resource.namespace`/ `.name`). | Absence of anything obvious in core semantic conventions, without checking the GenAI/MCP-specific ones. | Invalidated. | `mcp.resource.uri` already exists (`model/mcp/registry.yaml`, stability `development`, example `postgres://database/customers/schema`), but the spec only requires it "when the client executes a request type that includes a resource URI parameter": `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `notifications/resources/updated`. `tools/call` has no such parameter, so nothing requires the attribute there. Separately, even where it applies, it has no defined structure. The spec just says "the value of the resource uri," and the two example values given (`postgres://database/customers/schema`, `file:///home/user/documents/report.pdf`) do not share a format. The gap that remains is narrow and precise: when an agent reaches data through `tools/call` rather than `resources/read`, no standard attribute records what it touched. The claim therefore stands on two legs: scope (the attribute is absent on `tools/call`) and granularity (it is undefined where present). Neither example value reaches table level, so even where the attribute applies it cannot be relied on to identify a dataset. That is A05 seen from the semantic-convention side. | A maintainer checking the registry would have caught this in review. It is the same mistake as A02. |
| A05 | A span-level identifier and an OpenLineage dataset name are two encodings of the same identity, so the difference between the signals is essentially sampling. | Implicit in the "completeness" framing of Scenario 2. | Invalidated. | They are different kinds of identifier. `mcp.resource.uri` is a transport pointer, meaningful only to the server about to dereference it. An OpenLineage namespace+name is a catalog identity that has to be canonical to join a graph across producers and time, which is why OpenLineage has a dataset-naming specification at all. Neither derives from the other without a naming authority. The sampling argument is answerable with "turn sampling off". Identity semantics is not. This is the stronger argument, and the RFC leads with it. (See I16 for a real instance of the demo itself violating the naming convention, found and fixed.) | The RFC would have led with its weakest argument. |
| A06 | Parsing SQL text yields dataset identity complete enough to treat as the server's ground truth, i.e., pre- and post-execution routes differ in cost, not correctness. | Implicit in offering `openlineage-sql` as viable for instrumenting `execute_sql`, since it is what OpenLineage's own Airflow/dbt integrations use. | Invalidated. | Refuted by OpenLineage's own parser. Not "parsing is wrong" but "a parse is unverifiable from the inside". You cannot tell a complete parse from an incomplete one without asking the database, and a missing input produces no error and no visible gap. The upstream fix shipped in 1.53.0 (released 2026-09-01), one release after the 1.52.0 this workstream had pinned (A18). On the upgrade the strict `xfail` in `tests/unit/test_sql_parse_completeness.py` passed unexpectedly, which is what that file was written to signal, and the case stays as a regression test because a reintroduction would be silent.
